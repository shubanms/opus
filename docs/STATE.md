**ROADMAP V6 — the app talks back (2026-08-06).** Plan in `docs/ROADMAP_V6.md`. v5 built the *inputs* — effort on every set, weekly muscle volume, a streak that tells the truth — and none of it said anything back. v6 is the half that speaks.

**Shipped crash, fixed first (from the user's phone).** `MUSCLE_LABEL is not defined` on Home → Recovery and Progress → By Exercise. Moving the label map into `muscleTargets.js` I re-exported it with `export { MUSCLE_LABEL } from '...'`, which forwards a name *without* creating a local binding — so the six uses below it in `RecoveryMap.jsx` were all `ReferenceError` at runtime. Lint, build and 439 tests were all green. Three-part fix, because one would have been a patch rather than a guard:
- The binding (import, then re-export the imported name).
- **Biome `noUndeclaredVariables` promoted to error.** It is off by default in Biome's recommended set; it catches exactly this class.
- **The E2E route sweep now seeds history *and* clicks in-page tabs.** Both were needed and I got it wrong once: my first attempt only seeded, and the sweep still passed — the Recovery tab only *appears* once you have workouts, so loading the route never rendered the crashing component. Loading a page is not exercising it.

1. **Post-session verdict** — one honest paragraph when a session ends, computed at completion from volume-vs-average, records, effort ratings and set count, then stored on the workout row so it survives, re-reads in History, and reverts with a delete. Always both halves: praise alone is a slot machine, criticism alone is a nag. Every check is gated on having the data to be fair — no baseline means no "below average" (three prior sessions minimum), and an unrated session is asked for ratings rather than judged on intensity it never reported. With nothing to report it says so plainly instead of inventing a problem to look clever. **Caught in review:** the card rendered *below the fold* and passed the DOM assertion while invisible; it now sits above the Magnus bento row, with a viewport assertion, because "the element exists" is not "the user sees it".
2. **Loop-closer** — the beat the user asked for and almost no fitness app has: the app remembers what it told you and notices when you act on it. The verdict's concern is stored twice — as prose for a person, and as `advice` (`{key, metric, target}`) for the next session to check. Deliberate calls: the acknowledgement **replaces** the praise rather than stacking with it ("you did the thing I asked" *is* the compliment, and three clauses is a paragraph nobody finishes); advice has a shelf life of exactly **one** session, so skipping it means the next session raises its own concern on its own merits instead of the app relitigating something from three weeks ago; and when the advice was *not* followed it says **nothing**, because repeating the same criticism every session is nagging. Advice whose metric this build no longer understands ages out quietly rather than throwing. New E2E test drives a real session against a seeded open concern — verified to actually fail by removing the wiring, since the seam it covers (find the previous row, read the right field, keep the new session out of its own history) is invisible to every unit test.
3. **Quality-weighted XP** — base XP was weight × reps, i.e. volume, so the way to earn more was to do *more*, and the cheapest more is light filler. The game and the training were on opposite sides. The fix had to rest on something you cannot simply assert, which rules out RPE as the main lever: **intensity relative to your own best on that exact lift** (<50% → ×0.8, 85%+ → ×1.3, at-or-past your record → ×1.5). Per-exercise anchoring is what makes it fair — a 20 kg lateral raise against a 22.5 kg best scores as high as a heavy squat, so accessories are not punished for being light in absolute terms. Effort rating is a garnish on top, **upside-only and capped at +10%**: it is self-reported and therefore gameable, and docking unrated sets would just teach people to rate only their hard ones, corrupting the effort data the rest of the app reads. Three details worth keeping straight: the bests are read **before** the session's own PR rows are written, so a record set is scored against the record it beat rather than against itself; the crit bonus is added *after* the multiplier, because a dice roll is not an achievement; and `recomputeProfile` sums the stored `xpEarned` per workout, so nothing is re-scored retroactively — old sessions keep the XP they were awarded. The end-of-session modal shows the multiplier **with its reason** ("×1.30 · 2 sets near your best"), since a multiplier nobody explains is just a number that changed. *Deliberate and worth revisiting:* a programmed deload lands in the ×0.8 band. Kept, because those sets genuinely are easier and XP measures work done, not virtue — but it is a known tension with the app's own auto-deload.
4. **Streak rescue** — v5 made the streak tell the truth; this makes it survivable. The lapse is caught **the next time you open the app**, wherever you land, and the rest tokens you already earned are offered *there*. Retroactive by design: a PWA cannot reliably wake you (v5 research), so there is no honest way to warn someone at 9pm that today is the deadline — but noticing on the way back in costs nothing and needs no permission. A rescue is stored as `profile.streakGrace` (`{through, for}`, unindexed → no migration): the streak measures from the day the tokens bought rather than from the last workout, so history is never rewritten to pretend a session happened. Stamped with the `lastWorkoutDate` it was bought against, so it evaporates the moment that changes — training again, or deleting the workout it was anchored to, both invalidate it for free. Deliberate calls: **one token per day missed**, capped at 3 (past that the streak is genuinely gone, not for sale); the rescue buys you back to the **brink**, not to safety, so paying to skip a day does not also buy a day off; the offer is still *described* when you cannot afford it, because that is how someone learns what a rest token is; and declining is remembered against that specific lapse rather than "seen once". This is also the first time the app explains what a rest token is — they used to sit on Home as a bare "🛡️ 2 banked", a number with no mechanic attached, in the one place they could never be spent.
   - **Found while screenshotting it:** the shared `Modal`'s scrim carried `backdrop-filter` as an **inline style**, so the `html[data-fx]` switch — documented as the single control over the most expensive effect in the app — did not reach the surface that covers the entire screen, and neither did `prefers-reduced-transparency`. Now a `.modal-scrim` class behind both gates. (The ghosted double-image of the sheet visible in headless screenshots is the software rasteriser's backdrop-filter, not the app: it vanishes with the filter off and there is exactly one copy in the DOM.)
5. **Schedule-aware streaks** — the day-streak punished rest, which is the one thing every programme in the app prescribes: follow a Mon/Wed/Fri plan perfectly and it reads 1 forever, so the number meant to reward consistency instead rewarded overtraining. With a weekly plan the streak now counts **scheduled sessions hit**. Each scheduled day owns the window running to the next scheduled day, and training anywhere in it counts — being *late* is the case worth forgiving (missing Monday and lifting Tuesday is a session done, not skipped; a plan that calls that a failure is one people stop following). Without a plan there is nothing to be schedule-aware about, so `scheduleStreak` returns null and the day-streak stands. One hook, `useStreak`, decides which you are on and both return the same shape, because the alternative was threading a plan and a date list through six call sites — which is how a feature ends up half-applied, with Home saying one thing and Profile another. It also had to reach back into PR 4: without the live state, someone on Mon/Wed/Fri would have been offered a streak rescue **every Wednesday** for a streak their own plan says is intact. A scheduled rescue therefore prices in missed *sessions* and writes permanent `creditedDays` rather than a grace — the schedule streak is computed from dates, and training again must not revoke a session you paid for.
   - **Bug the E2E caught that nothing else would have:** I put `useStreak()` after ProfilePage's `if (!loaded || !profile) return null`, so the hook count changed between renders — React error #310, a blank error screen on Profile. Lint, build and 604 unit tests were all green; the route sweep found it in seconds. Hooks above the early return.

**On-device fixes (from the user's phone, first live review of Aurora):**
- **Magnus was invisible.** My Phase-1 retint did `o.material = mats.map(...)` and *then* checked `if (!Array.isArray(o.material))` to unwrap — always false, because the map had just made it an array. Every single-material mesh kept a one-element array, and Three.js needs matching geometry groups to draw an array material, so it rendered nothing and threw no error. The `wasArray` check now happens before the map. Note this was **not** the shader/two-WebGL-contexts theory I flagged — an isolation test disproved that.
- **Bottom nav was see-through**, with page text clearly readable under it. `.glass-strong` used `color-mix(in srgb, var(--color-chalk) 88%, transparent)`; replaced with an explicit `--glass-chrome` rgba token per theme at 94%, so what ships is exactly what's written.
- **Content ran under the nav** — `main` had a fixed `pb-24` that ignored `env(safe-area-inset-bottom)`, so the last card sat beneath the bar on a gesture-nav phone. Now `calc(104px + env(safe-area-inset-bottom))`.
- Lesson recorded: a WebGL canvas can't be verified with `readPixels` (returns zeros without `preserveDrawingBuffer`) — screenshot the composited region instead. My first isolation test was invalid for exactly this reason.

**Phase 5 (workout screen) DONE** — the screen you stare at between sets, so the work was legibility and reach, not decoration. Logged-set numerals up to `text-base`, entry fields to `text-lg` with taller rows, and the note/delete icons padded into real touch targets (they were 13px glyphs with no padding — a hard tap with chalky hands). Log button is now a 48px gradient tile with an accent glow when it's armed. Set rows animate in and collapse out via `AnimatePresence` + `layout`; crit sets carry an accent wash so the achievement lives on the row rather than only in a float that vanishes. Rest-timer ring uses the theme track instead of a hardcoded `#444`.
**Exercise sections gained active/done states** so a glance answers "where am I?". Two rules worth keeping straight: **done** means a *target was actually met* (an ad-hoc session has no targets, so nothing is dimmed — logging two sets of bench doesn't mean you're done with bench), and **active** is the exercise you logged to *most recently* (derived from `completedAt`), falling back to the first not-done one before anything is logged. My first pass got both wrong: it dimmed any exercise with ≥1 set and lit the first incomplete one, which pointed at the wrong card the moment you started.
**Phase 6 (charts) DONE — Recharts replaced by visx.** Recharts was the last thing on screen still wearing someone else's default look, and its geometry wasn't restylable enough to fix: axis label collisions, hover tooltips, a stock radar. Swapped for **visx** (`@visx/scale`, `@visx/shape`, `@visx/curve`) — scales and shape generators, no chart chrome — with the chrome written here.
- **`src/components/charts/`** is now the whole chart language. `ChartFrame` owns everything shared by the cartesian charts (measure → scales → grid → axes → scrub → readout) and takes the plot as a render prop, so line and bar cannot drift apart. `TrendChart` draws through an accent-gradient stroke with a fading area and a `pathLength` draw-on; `VolumeChart` lays one violet→teal gradient across the plot in **user space**, so the bars sample a single continuous sweep rather than each being painted identically. `RadarChart` is deliberately *not* visx: five points on a circle is geometry, and hand-rolling it keeps one angle convention shared by the polygon, the vertex dots and the label placement.
- **Inspection is drag-to-scrub, not hover tooltips.** A hover tooltip is a desktop idea — on a phone it degrades into poking at a series point by point. Put a thumb down, drag, and each point you cross ticks the haptic motor once (touch only; a mouse buzzing the device would be absurd). The readout flips to the far side of the chart so it never sits under the finger.
- **Colour comes from CSS custom properties on SVG attributes** (`stroke="var(--color-gold)"`). No JS reads computed styles, so a theme flip recolours every chart with no re-render — and the three hardcoded hexes each old chart carried are gone.
- **New pure util `chartMath.js`** (+40 tests): `niceTicks`, `padDomain`, `compactNumber`, `nearestIndex`, `tickIndices`, `roundedTopRect`, `radarPoint`, `polygonPath`, `radialAnchor`.
- **Bug caught in review, not on a device:** the x-axis rendered `07-0607-12` — two labels on top of each other. `tickIndices` spread `max` evenly-rounded fractions across the series, which puts *adjacent* indices next to each other (10 points into 7 slots → 0,2,3,5,6,8,9). Now a fixed stride, with property tests asserting no two labels are ever within one point of each other across every count×budget combination.
- **Light mode fixes found by screenshotting both themes:** dimmed bars at 0.3 opacity vanish entirely against the near-white ground (now 0.45), and the radar's vertex halos used `--color-chalk` — right on a card that follows the canvas, wrong on the character card, which is `--color-stone` and dark in *both* themes.
- **Bundle: main chunk 335 KB → 243 KB gzipped (−89 KB, −27%)**, measured against the live Phase-5 build. Recharts and its d3 dependencies were in the main chunk; the three visx packages are a fraction of it.
- Verified: 408 unit tests, 8/8 E2E, lint (0 errors, 222 warnings — unchanged) + build clean, and every chart driven and screenshotted in both themes against seeded history.

**Phase 7 (cinematics) DONE — and the user chose no skip button.** That decision is what shaped the whole design: if a celebration cannot be dismissed, its *length* is the only thing protecting the person holding the phone, so length became the engineering constraint.
- **The queue is the real change.** Finishing a session could already fire a level-up screen, an achievement toast and a particle burst *simultaneously*, stacked on top of each other, each owned by `WorkoutPage` — the component about to unmount. Now `cinematicStore` holds an ordered queue and one `CinematicHost` in `AppLayout` plays it. `WorkoutPage` hands over the whole result and forgets about it.
- **A PR finally has a screen.** The single most meaningful event in the app got a one-second particle burst and a toast; everything else got the same. Now the record counts up *from the record it beat*, so you watch the old number get passed rather than being told afterwards. Level-up was rebuilt on the OPUS monogram — the number sits inside the ring, which already thickens and gains a stud per level, so the mark literally grows with you. Dungeon clear went from a toast to its own screen.
- **Pacing, because nothing can be skipped.** Many records collapse into one cinematic (three sets of three lifts can produce nine at once) with the rest counted on a chip. The queue then *speeds up* as it grows — a rare four-event session plays as a faster montage, not a longer slog. Worst case is ~5.5s, asserted by a test.
- **Bug caught in review:** the pacing shortened each cinematic's duration but not its entry-delay schedule, so a sped-up dungeon clear introduced its last line as the screen was already leaving. The `scale` now travels with the queue item and multiplies every delay and count-up.
- **The host's timer is load-bearing** and treated as such: it is the only thing that ends a cinematic, and it sits *outside* the error boundary so a cinematic that throws still advances the queue instead of freezing the app behind a screen with no way out. A new E2E test asserts the queue always drains with no interaction — and was verified to actually fail by sabotaging the timer, because a test that cannot fail proves nothing.
- **Effects off degrades to toasts** via a pure `summarize()`. A full-screen takeover is exactly what that setting asks not to see, but being told you levelled up is information, not decoration. Verified: zero takeovers with effects off, all four events still reported.
- Also: `Particles` gained a `z` prop — the stage sits above the toast layer, because a full-screen celebration with "+85 Iron earned" poking through the bottom reads as a rendering fault. `CountUp` gained `from`. `LevelUpScreen` and `AchievementToast` deleted.
- Verified: 426 unit tests (18 new), **9/9 E2E** (one new), lint 0 errors / 219 warnings (down 3), and both sessions driven end-to-end in a real browser in both themes. The cinematics are deliberately dark in both themes — a celebration is a lights-down moment.

**ROADMAP V5 — the feedback wave (2026-08-05).** Plan in `docs/ROADMAP_V5.md`. The user's diagnosis started it: *"it's all input, I'm feeding it a lot of data but not getting any feedback from that"* — plus a suspicion that the streak was broken. It was. Eight PRs, each verified in a real browser and pushed green:

1. **Streak truth** *(bug)* — `profile.streak` is written in exactly one place, `completeWorkout`, so nothing recomputed it as days passed. A 12-day streak that ended last week kept reporting "12" on Home, Profile and Progress, correcting itself only, silently, on the next session. New pure `streak.js` derives live state (safe / at risk / broken) from the stored count plus the calendar — no history scan, no migration. The radar's Consistency axis and the Home aura were both inflated by dead streaks; Magnus was congratulating them. **One thing deliberately still reads the stored value**: the streak-break XP penalty is about the streak you *lost*, and the live count is 0 once broken — passing it there would silently kill the rest-token mechanic.
2. **Effort rating** — RPE had been stored on every set for ages, but asking cost three taps *before* logging, behind a toggle that reset each time. The field stayed empty so nothing could be built on it. Now the set you just logged asks once (Easy / Hard / Max), mapped onto the same 6–10 scale so storage and CSV export are untouched. The old pre-log picker was removed rather than left alongside. Caught while removing it: a leftover `setRpe(null)` call to a deleted setter that would have thrown on every logged set — neither lint nor build flags that; driving a session does.
3. **Faster logging** — weight steppers moving by a pair of your lightest plate (snapping to the grid, so 62.5 + 5 reaches 65 not 67.5), fields no longer cleared after logging (a repeat set is one tap), and prefill from the last set you actually did, warm-ups skipped.
4. **Session-live indicator** — a breathing halo and running clock on the centre action, visible from every tab. Long-press during a session offers the way back instead of three ways to start another. Also deduped `formatDuration` (three byte-identical private copies) into a tested `duration.js`.
5. **Smart rest** — the timer retargets from the effort rating. The interesting part is timing: the rating arrives *after* the clock starts, so it retargets in place rather than restarting, which would throw away seconds already rested. The suggestion is a multiplier on the user's own default, not a flat override.
6. **Weekly muscle targets** — this week's working sets per muscle against a target, with neglected muscles surfaced (an absent row cannot be noticed) and the push/pull ledger. Thresholds are forgiving: "over" only past 150%, and the balance verdict says nothing below six sets. Moved `MUSCLE_LABEL` out of RecoveryMap into the util — shared data living in a component meant a node-env test had to drag the render tree along.
7. **Swap suggestions** — swapping opened the full 82-entry picker and left you to search, which is backwards. Now ranked same-muscle alternatives, and the ranking rests on one observation: you swap because the *equipment* is unavailable, so a different implement ranks above a near-identical one. Browse-all remains the escape hatch.
8. **UX sweep** — empty states became doors (History, Records and the weekly targets all offer "Start a workout"), and Settings gained a jump-to-section row; with a fixed known set of sections, a table of contents beats a search box.

**Visual bug caught in review:** chart x-axis labels collided again ("6/156/22"). The label budget assumed DM Mono had loaded — the system fallback is wider, which is what an offline first paint gets. The estimate now errs wide, costing at most one label.

**Notification research (verified, not assumed):** the Badging API **does not work on Android** (it does on desktop and iOS) — but Android badges an installed PWA automatically when there's an unread notification, so it is free with a notification rather than a feature to build. Notification Triggers is dead (two origin trials, never shipped). No scheduled-local-notification API exists on the web at all. Periodic Background Sync is Chromium-only, installed-only, engagement-gated — and its frequency tracks how often you use the app, meaning it is least likely to fire exactly when a streak nudge matters most. Conclusion recorded in the roadmap: design the streak so it never depends on being woken.

## UX standard (keep for all future work)
- Bottom-sheet modals cap at 90vh with fixed header + scrollable body (never push off-screen top)
- All pages render inside AppLayout main with pb-24 for BottomNav clearance
- Destructive actions (delete) require confirm; full data wipe requires typing "DELETE"
- Design for an Android phone screen first: compact filters, generous tap targets,
  give content (lists) vertical priority over chrome. Settings reachable via gear on Profile.
- Full reset: Settings → Danger zone → type DELETE → wipeAllData() clears all tables +
  localStorage, then reloads to BASE_URL for a clean start.

## Data-integrity principle (keep for all future work)
Anything addable must be removable/editable/deletable, and deletes must revert
ALL derived data. Reference: `deleteWorkout` reverses sets, energy logs, PRs
(recomputed), and XP/level/title/streak (recomputed from remaining workouts).
- Workout XP is stored as the full gained amount per workout (`xpEarned`), so the
  profile can be rebuilt by summing remaining workouts.
- `recomputeProfile()` / `recomputePRs()` in utils/workoutActions.js are the
  canonical rebuilders — reuse them after any deletion that affects history.
- Custom exercises: deletable (cascades sets/PRs/template refs + refreshes
  workout totals). Body-stat & sleep entries: deletable. Built-in seed
  exercises are intentionally not deletable.
